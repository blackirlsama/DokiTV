# P0：业务身份、视频授权与指标对账

更新：2026-10-22。Agent 仍是独立模块，通过 HTTP 调用业务服务；业务服务验证现有 JWT 与 Redis 在线会话，并以固定 SQL 查询数据。

## 接入边界

- `IdentityPort` 的默认实现保持 Demo 兼容；business 适配器支持按创建请求、任务和会话授权。视频目标来自显式问题和经过拥有者校验的澄清来源，不枚举用户全部视频。
- 业务服务用 JWT 的 subject 取得 userId，校验签名/有效期、Redis 中的当前 Token、用户未删除和配置的正常状态。客户端传入的 userId/tenantId 不参与授权。
- 首版只允许查询自己发布且未删除的视频，无管理员隐式放行。请求进入、结果读取和实际业务 SQL 均检查当前权限；工具查询还会重新检查登录状态。
- 原始 Token 只保存在 Agent 进程的有界内存中，最多 1024 个上下文，空闲 10 分钟到期。快照中的 authorizationRef 是随机引用，不能作为登录凭证，不包含 Token。
- Agent 重启后能使用新登录验证读取已完成记录。旧的在途任务不重放；旧排队任务若缺少原凭证上下文，会受控失败为 AUTH_CONTEXT_EXPIRED，需要重新提交，不从数据库恢复明文凭证。
- 历史消息按本次授权的视频集合过滤；读取会话消息时重新验证当前页涉及的视频。视频归属变化后，旧答案、产物和相关历史不再对旧拥有者开放。

## 指标定义

首版 `bullet_count` 的版本为 `bullet-retained-created-v1`，数据源为 `mysql:bullet:retained-persisted-v1`：按 `bullet.create_time` 的指定日期，统计**当前已入库且仍保留的弹幕记录**。

这不是历史发送总量。旧数据被物理删除后不计入；异步 MQ 未落库的数据不计入；历史缺少发送时间的消息无法事后推断真实发送日期。工具结果的 complete 表示对这一已入库集合完成 COUNT，不证明 MQ 消费完整。框架会在最终答案追加不可被模型省略的口径说明。

日期按 Asia/Shanghai 解释，只接受最近 30 天内已结束日期，使用 `[当天零点, 次日零点)`。TIMESTAMP 使用 UTC 连接和 UTC 参数；DATETIME 使用明确配置的存储时区，不能猜测旧字段的时间含义。

`video_stats.bullet_count` 为累计计数，不用于回答按日问题。对账时分别比较：按日工具值与明细 COUNT、累计计数与全部保留明细；不能把一天的数量与累计计数直接相减。

## 业务接口

| 路径 | 行为 |
|---|---|
| GET /internal/agent/principal | 校验登录并返回可信 tenantId/userId |
| POST /internal/agent/authorize | 接收 videoIds，返回当前拥有的子集，最多 100 个目标 |
| GET /internal/agent/metrics?videoId=...&date=...&metric=bullet_count | 重新验证登录；视频归属、删除状态和 COUNT 在同一 SQL 语句中检查 |

接口使用 `Authorization: Bearer <现有登录Token>`。原业务拦截器兼容 Bearer 和旧裸 Token。新增接口默认关闭；独立业务桥接应用显式开启。

## 两种业务侧启动方式

在原 Tianmu 服务中开启：设置 `AGENT_BRIDGE_ENABLED=true` 和 `BUSINESS_ACTIVE_USER_STATES`，然后按原方式启动业务服务。接口路径包含原业务应用已有的 context-path，配置 Agent 的 BUSINESS_BASE_URL 时一并包含。

独立运行只读桥接入口：在仓库根目录执行 `mvn -B package`，产物是 `target/tianmu-0.0.1-SNAPSHOT-agent-bridge.jar`。它使用与业务服务相同的 JWT 工具和在线 Redis，不启动业务的 WebSocket、Canal 等组件。

通过部署环境注入：

| 变量 | 用途 |
|---|---|
| BUSINESS_JDBC_URL | 业务 MySQL URL；凭证单独注入 |
| BUSINESS_DB_USER / BUSINESS_DB_PASSWORD | 推荐只授予 user/video/bullet 的 SELECT 权限 |
| BUSINESS_REDIS_HOST / BUSINESS_REDIS_PORT / BUSINESS_REDIS_PASSWORD / BUSINESS_REDIS_DATABASE | 必须指向实际登录会话所在的 Redis 与相同数据库索引 |
| JWT_SECRET_BASE64 | 与业务登录服务相同的新签名密钥；至少 32 个随机字节再 Base64 编码 |
| BUSINESS_ACTIVE_USER_STATES | 必填，填写实际 user.state 的正常值，例如测试库为 normal；不按示例猜生产值 |
| BUSINESS_TENANT_ID | 服务端租户标识，默认 tianmu |
| BUSINESS_DATETIME_ZONE | 实际 DATETIME 存储时区，默认 Asia/Shanghai；TIMESTAMP 不受此选项影响 |

```powershell
java -jar target/tianmu-0.0.1-SNAPSHOT-agent-bridge.jar
```

独立入口默认只绑定本机 8202。业务查询使用私有的 UTC 只读 Hikari 池，与原写连接池分离；查询超时 2 秒，连接和套接字超时 3 秒。嵌入原应用时，可通过 BUSINESS_JDBC_URL 等变量单独指定只读账号；未提供时克隆原 Hikari 的连接信息创建独立只读池，不修改原连接的时区。

部署前检查 `(video_id, create_time)` 索引；供审阅的脚本位于业务模块 `src/main/resources/db/manual/agent-metric-index.sql`。不在启动时修改业务表结构。SQL 对账模板见同目录的 `agent-metric-reconcile.sql`。

## Agent 启动

设置 `BUSINESS_BASE_URL` 指向上述业务服务，再设置 Agent 专用库的 AGENT_JDBC_URL、AGENT_DB_USER、AGENT_DB_PASSWORD，以及 Redis/对象目录。业务库与 Agent 存储库分别配置。

模型仍通过 DEEPSEEK_API_KEY 注入，分别使用预处理与 Harness 模型：

```powershell
java -jar target/operations-agent-0.7.0-SNAPSHOT.jar --spring.profiles.active=business,deepseek,persistent
```

此 profile 没有 Demo 身份和 Demo 查询降级。业务服务或登录验证不可用时失败关闭；FAQ 使用业务能力说明文件 `faq/business.json`。

请求示例：

```http
POST /api/agent/runs
Authorization: Bearer <Tianmu登录返回的Token>
Idempotency-Key: my-query-001
Content-Type: application/json

{"message":"查询视频1001昨天的弹幕数"}
```

## 弹幕入库修复

WebSocket 在发布前生成稳定 bulletId 和服务端接收时间；消费者沿用这一 ID。入库以视频行锁协调同视频并发，重复事件不会再次插入或增加计数；同 ID 内容冲突会失败。记录、计数初始化和计数增加处于同一事务。

保存失败会从消费者抛出，交由 RocketMQ 的重试/DLQ 策略处理，不再吞异常。缺少时间的历史消息会记录告警，以入库时间作为创建时间，不声称还原原始发送时间。

## 验证与复现

业务测试需显式 `BUSINESS_IT=true`，JDBC 必须指向本机、库名以 `_it` 结尾。测试表结构只在 src/test/resources，生产 JAR 不包含测试发令牌工具。

1. 仓库根目录运行 `mvn -B package`，Agent 模块运行 `mvn -B package`。
2. 使用测试专用库和 Redis，运行测试类 BusinessFixtureMain，输出私有 fixture JSON。该工具建立两个用户、三个视频和跨日期边界的弹幕，并生成与实际登录相同格式的 JWT；不要提交生成的凭证文件。
3. 使用 `scripts/verify_business_flow.py` 启动两个 JAR。模型通过本地 HTTP 模拟器驱动，认证、授权、查询和持久化使用真实实现。
4. 如果需要真实模型验收，运行 `scripts/probe_real_business_model.py`，它从环境读取 DEEPSEEK_API_KEY，会产生受 Agent 调用次数预算限制的真实模型请求。

两个脚本均需要 `--jar`、`--business-jar`、`--fixture`、`--java`、`--mysql-client`、`--env-file`、`--output-dir`。env-file 放在仓库外，包含 BUSINESS_* 和 AGENT_* 配置；output-dir 为新目录。完整运行结果见 [P0业务接入验收](P0业务接入验收.md)。

当前业务验证使用隔离库中的受控数据。正式业务账号、现有数据分布、线上查询计划、MQ Broker 重投/死信链路和生产吞吐需要在实际部署环境继续验收。
