# 上下文与记忆管理设计建议

日期：2026-10-21。状态：参考材料的吸收方案，尚未实现；接口名称为建议，不代表当前已有代码。

存储职责、会话快照、近期视图、正式消息与终态事务的详细后续方案见 [存储体系设计](存储体系设计.md)。其中 20 条读取、8 条近期原文、16000 字符采用可调试验初值；不作为模型无关的固定保证。2026-10-22 更新：v0.7 已实现近期会话投影、Redis 回源和显式澄清续接，详见 [持久化存储接入](持久化存储接入.md)；工具视图压缩、长期记忆和完整预算仍未实现。

## 1. 采用的思路

把请求内工具结果、跨请求对话历史和整体模型输入分别管理。优先使用确定性规则压缩；为当前问题、可信指令、权限及证据保留明确边界。利用已有 CONTEXT Transform 扩展模型输入处理，固定预算检查由 Harness 保证执行。

不沿用材料里的 200k Token、最近 20 条或 16000 字符作为通用默认值。实际阈值应随模型窗口、输出预留、工具规模及评测结果确定。

## 2. 原始证据与模型视图分开

建议形成以下数据流：

```text
业务工具 → 参数/权限/结果校验 → 原始证据或 Artifact 保存
                               ↓
                    生成有大小上限的模型可见视图
                               ↓
会话历史 → MemoryBuilder → CONTEXT Hook 链 → 固定预算检查 → 模型适配器
```

EvidenceStore 保存事实来源和完整统计口径；ArtifactStore 保存较大的结果。模型只看到摘要、关键字段和受控引用。压缩不能修改原始证据，最终答案的证据校验继续查询原始记录。

目前证据仍在任务内存里，已有 read_result 工具也不等于具备大文件存储。新增外置引用必须带归属、大小、摘要哈希、有效期及可读取范围；读回时重新检查权限并限制返回大小，避免再次把大结果整个塞回模型。

当前 TransformInvariants 会保护 ToolResult 内的事实字段，TransformDispatcher 还会在插件执行前检查输入大小。不能简单加一个截断 Hook 就声称支持超大工具结果。需要先定义独立的模型视图契约，并在业务适配器/工具入口限制、分页或外置大结果，避免在压缩前就耗尽内存或触发大小拒绝。

建议模型视图至少保留：调用 ID、工具名、规范化参数摘要、成功/失败、evidenceId/artifactId、统计口径、完整性标记，以及 originalSize、compacted、truncated。数字事实优先按结构化字段提取，避免用正则从任意 JSON 中猜指标。

## 3. 压缩边界和执行顺序

| 层次 | 职责 | 保护边界 |
|---|---|---|
| 工具结果准入 | 限制大小、分页、保存原始结果，产出模型视图 | 不丢失来源、失败状态、关键指标与证据引用 |
| MemoryBuilder | 开始请求时读取有限条历史，最近消息保留较多，更早消息规则摘要 | 当前问题独立保存；历史带角色、顺序和来源 |
| ToolResultContextHook | 每次调模型前，压缩较早工具视图 | 保留最近必要结果及读取引用；与工具调用记录成对处理 |
| ContextBudgetGuard | 计算完整输入预算，不够时按确定顺序降级，仍不够则拒绝调用 | 可信指令、当前问题、权限和必要工具 Schema 不可任意截断 |

建议降级顺序：先减少旧工具正文，再缩减旧对话，最后减少非必要检索片段。达到硬上限仍不能满足时，返回明确的上下文预算错误或要求用户缩小问题，不发送超限请求。

需要分别记录“当前用户请求边界”和“最近一次工具调用边界”。参考材料一处允许压缩本请求内较早工具结果，另一处又说整个当前循环完全不压缩，两者需要统一。这里选择：当前问题和最近必要工具结果优先保护，本请求内已使用的旧结果也可转成可恢复摘要；原始证据始终保留。

提供商要求的工具调用/结果消息结构必须保持合法，不能单独删除结果留下悬空调用。具体投影由模型适配器负责，并对最终实际发送的消息再次计量。

“已调用过，请勿重复”可以作为提示，但防重复仍依赖服务端规范化参数和调用记录。明确暂时故障的重试、重新授权或数据版本变化要与已成功同参调用区分。

## 4. 两种预算需要独立

**上下文窗口预算**约束一次模型调用能发送多少内容；**累计 Token / 费用预算**约束整个任务能花多少资源。压缩只减少当前输入，不会退回已经产生的费用。

```text
可用输入额度 = 模型窗口 - 预留输出 - 提供商协议开销 - 安全余量
本次输入消耗 = 指令 + 当前问题 + 历史 + 工具 Schema + 工具结果 + 其他模型输入
```

有可用 tokenizer 时按对应模型计量。没有时采用经过样本校准的保守估算，并记录估算方法；chars / 2.5 仅可作为粗估，中文、代码和 JSON 的比例不同，不能保证不超限。硬限制仍由模型配置、适配器校验和错误处理共同兜底。

收尾调用同样必须经过预算检查，沿用原请求截止时间，预留输出 Token 并计入任务消耗。若未来启用长思考等能力，也需按提供商语义预留和结算。

## 5. 跨请求记忆和存储

第一阶段建议只保存已提交的用户问题、最终答复、必要的证据/产物引用与状态。澄清状态单独建模；仅保存问答无法自动恢复未完成任务。跨请求引用旧证据时重新鉴权，并说明数据时间；失效或过期时重新查询。

会话数据以服务端解析出的租户、用户、会话组成归属键。引入消息序号、requestId 幂等键、容量上限、TTL 与删除策略。请求开始捕获历史版本，避免并发请求把别人的新消息混入当前上下文；用户新消息是否中断旧任务应由会话协调器明确决定。

Redis 可承载有界的近期会话窗口，但不预设其为唯一记录源。是否保留长期对话、如何审计和恢复，再决定持久化数据库与 Redis 的关系。MySQL 存放有索引的会话消息本身也是可行方案，不能仅因写入频繁就判定不可用。

若采用 Redis，优先设计有界 ZSet / Stream 等按序读取方式；不对无限增长的 Hash 做 HGETALL 后截取。若用 Hash + ZSet，需要原子写入、裁剪和过期处理。Redis 单线程仅保证单条命令串行执行，多条 HSET/SADD/EXPIRE 不自动组成原子事务；需按具体语义使用 Lua 或事务，并处理 Cluster 同槽约束。

类型/标签索引按实际查询需求增加。跨会话索引需要独立的权限过滤、分页、过期和删除清理，避免正文过期后索引永久残留；首期普通会话续聊无需先做这些索引。

“历史仅作背景”分隔符可以帮助聚焦，但不是提示注入防线。旧消息、检索文本和工具内容均应保留不可信来源属性，不能拼接成可信系统指令；工具端权限检查始终生效。

## 6. 建议的扩展接口与实施顺序

| 建议接口 | 责任 | 可由谁独立实现 |
|---|---|---|
| ArtifactStore | 大结果写入、受控读取、容量与过期管理 | 存储同学，先本地实现再接对象存储 |
| ToolResultProjector | 将原始结果投影成可压缩的模型视图 | 工具负责人，与证据契约共同评审 |
| ContextSizer / ContextBudgetPolicy | 模型输入计量、预算分配和硬门控 | Harness 与模型适配负责人 |
| ConversationMemoryStore / MemoryBuilder | 有界读取、消息幂等、历史组装 | 会话同学；依赖先冻结会话身份与消息契约 |
| ToolResultContextHook | 按顺序压缩模型视图 | Hook 同学；不得修改原始证据 |

建议先完成循环控制验收，再落地“工具视图 + 大结果引用 + 输入预算”，最后增加跨请求会话、澄清恢复及 Redis 实现。暂不引入长期语义记忆、自动向量召回或额外的模型摘要调用。

验收应覆盖：大结果不会先撑爆内存；压缩不改数字和证据；当前问题保留；工具协议完整；中文/JSON 输入预算；预算不足明确终止；跨用户引用拒绝；过期引用可解释；重复写入幂等；并发会话顺序；取消期间不继续读写；收尾也执行预算；Trace 只记录压缩前后大小、策略与错误码等受控元数据。
